# Vision · 에이전트-직원 기반 조직

> **⚠️ 이 문서는 특정 전제(제품명·조직 구조·지표·도구 선택) 를 가진 개인 설계 초안입니다.** 일반화된 프레임워크가 아니라 "이렇게 잡으면 어떤 모양이 되는가" 를 보여주는 **샘플 설계** 로 읽고, 본인 컨텍스트에 맞춰 포크·수정해 사용하세요. 자세한 안내는 [`platform/docs/README.md`](./README.md) 상단 공지 참조.

## 한 줄 요약

> **"CEO 1 명이 Slack 으로 1 명의 비서와 6 명의 C-suite AI 리더를 통솔하고, CTO 아래 5 명의 개발 서브워커가 실제 코드를 만든다."**

사람 직원이 아닌 **자율 에이전트**가 Slack 에서 실명으로 일하고, 커밋·PR·보고·에스컬레이션 모두 사람과 동일한 프로토콜로 수행한다.

## 왜 이렇게 하는가

### 출발점

claude-cockpit 은 원래 CEO 1 인의 Claude Code dotfiles 였다. 세 가지가 동시에 겹치면서 설계 목표가 바뀌었다:

1. **Claude Code 가 대화 도구가 아니라 "일하는 주체"가 될 수 있음** — Agent SDK · MCP · 서브에이전트 · 훅이 이 전환을 가능하게 한다
2. **1 인 창업자의 병목은 "생각하는 시간" 이 아니라 "손발의 수"** — 리더 6 명을 AI 로 복제하면 CEO 는 전략·승인·방향성에만 집중
3. **같은 cockpit 인프라를 미래에 확장** — 사람 직원이 들어와도 동일한 정책·툴·메모리 체계를 자동 상속

### 핵심 명제

> **에이전트는 단순한 도구가 아니라 "고용된 직원" 이다.**

이 명제가 모든 후속 설계를 지배한다. 귀결:

- 각 에이전트는 **고유 정체성** (Slack user, GitHub App, Git committer) 을 갖는다. 공유 자격증명 금지
- 각 에이전트는 **고용 계약서** (`AGENT.md`) 를 갖는다. 역할 · 권한 · 승인 게이트 · 예산 · 에스컬레이션이 명시됨
- 각 에이전트는 **장기 기억과 단기 기억** 을 분리해 가진다. 역할 · 경계 · 회사 사실은 불변, 경험은 가변
- 각 에이전트는 **예산** 을 갖는다. 초과 시 자동 정지
- 각 에이전트에게는 **해고 스위치** 가 있다. `/agent stop @name` 한 줄로 회수
- 각 에이전트는 **동일한 조직 톤·정책** 을 상속한다. 모두 같은 `core/CLAUDE.md` 를 읽음

## Secretary — CEO 운영 보조 1 명

C-suite 와 동급이 아닌 **CEO 직속 운영 레이어**. 도메인 책임이 아니라 "CEO 의 하루" 를 책임진다.

| 항목 | 값 |
|---|---|
| **Slack 핸들** | `@Secretary` (또는 `@COS`, Chief of Staff) |
| **디렉토리** | `workers/secretary/` |
| **홈 채널** | `#ceo-office` (DM 우선, 공개 포스트 자제) |
| **주 책임** | 일일 브리핑, 캘린더/이메일 1차 처리, 리더 간 메시지 라우팅, TODO 추적, 외부 요청 스크리닝 |
| **권한** | **읽기 우선**. 쓰기는 전부 HITL (외부 발송 · 일정 확정 · 계약 서명 전부 CEO 승인) |
| **도구** | Google Calendar MCP, Gmail MCP, Notion/Linear (읽기), 리더 봇 멘션 권한 |

**서브에이전트와의 차이**: `humans/subagents/ceo-briefing.md` 는 CEO 의 Claude Code 세션 안에서 일회성 호출되는 Task 툴. Secretary 는 Slack 에 상주하며 그 서브에이전트를 *사용하는* 상시 봇이다.

## 6 명의 C-suite 리더

CEO 가 직접 대면하는 AI 리더는 6 명이다. 실제 회사의 임원진과 1:1 매핑된다.

| 도메인 | Slack 핸들 | 디렉토리 | 주 책임 |
|---|---|---|---|
| 재무/회계 | `@CFO` | `workers/cfo/` | 월마감, 지출 리뷰, 예산 편성, 현금흐름 리포트 |
| 마케팅 | `@CMO` | `workers/cmo/` | 캠페인 기획, 카피 리뷰, 지표 분석, 경쟁사 모니터링 |
| 기획/프로덕트 | `@CPO` | `workers/cpo/` | PRD 초안, 사용자 스토리, 로드맵, 우선순위 |
| 디자인 | `@Design` | `workers/design-chief/` | 디자인 리뷰, 디자인 시스템, UX 피드백 |
| 데이터 | `@CDO` | `workers/cdo/` | 지표 질의, 대시보드, 실험 분석, 데이터 품질 |
| 개발 | `@CTO` | `workers/cto/` | 코드 리뷰, 아키텍처 결정, PR 머지 게이트, 장애 대응 |

**통신 프로토콜**:

- CEO ↔ 비서: Slack DM 또는 `#ceo-office` (브리핑 · TODO · 잡무)
- CEO ↔ 리더: Slack DM 또는 리더 홈 채널 (`#finance`, `#engineering` 등)
- 비서 → 리더: `#ceo-office` 스레드에서 멘션 (CEO 대신 질의 · 일정 조율)
- 리더 간: `#leaders-lounge` 채널 스레드 협업
- 리더 → 서브워커: CTO 만 해당. DM 또는 `#eng-*` 채널
- 시스템 이벤트: 전부 `#agent-ops` 로 자동 스트림
- 패닉 버튼: `#agent-admin` 에서 `/agent stop-all`

## CTO 하위 서브워커 5 명

개발 리더만 유일하게 계층 조직을 가진다. 제품 레포(`<product>`)의 디렉토리 경계와 일치시킨다.

| 서브워커 | Slack 핸들 | 작업 범위 |
|---|---|---|
| backend-dev | `@backend-dev` | `services/**`, `platform/{gateway,account,profile,community,social,commons}/**` |
| frontend-dev | `@frontend-dev` | `platform/frontend/**` |
| qa-dev | `@qa` | `e2e/**`, 각 서비스 테스트 |
| devops-dev | `@devops` | `ops/{docker,ansible,scripts}/**`, `.github/workflows/**`, `docker-compose.yml` |
| infra-dev | `@infra` | `ops/{terraform,kubernetes,infra}/**` |

라우팅은 `workers/cto/delegates.yaml` 에 선언적으로 정의된다. CTO 가 요청을 받으면 해당 파일의 규칙에 따라 Task 툴로 서브워커를 호출하고, 결과를 CEO 언어로 종합해 응답한다.

## 핵심 설계 원칙

### 1. 계층은 실제 조직도를 따른다

CEO 는 리더 6 명만 안다. CTO 아래에 누가 있는지는 CTO 가 관리한다. 현실 조직과 은유가 맞지 않으면 사용자가 혼란스럽다.

### 2. AGENT.md 가 진실의 원천

한 에이전트의 모든 것 — 권한, 트리거, 예산, 페르소나, Slack 매니페스트, 메모리 시드 경로 — 이 `workers/<name>/AGENT.md` 한 파일에서 파생된다. 이 파일이 곧 고용 계약서이며, 변경은 PR 리뷰 대상이다.

### 3. 정책은 core/, 역할은 workers/

- `core/CLAUDE.md`: 회사 공통 톤·언어·가드레일 (한글·존댓말·코딩 원칙)
- `workers/<name>/persona.md`: 개별 역할의 성격 · 의사결정 스타일
- 모든 worker 가 `core/` 를 자동 상속. 개별 persona 는 덮어쓰지 않고 덧붙인다.

### 4. 승인 게이트가 있어야 자율이 안전하다

- 코드 수정: 브랜치 위 · PR 로 제출 · **머지는 사람**
- DB 마이그레이션, 프로덕션 배포, 외부 커뮤니케이션: **반드시 HITL** (리액션 승인)
- 파괴적 동작 (`rm -rf`, `drop table`, `terraform destroy`): deny 기본 + 예외 시 명시적 승인

### 5. 실패는 조용할 수 있으므로 감사가 필수

- 모든 worker 동작은 `audit.log` 에 JSONL 로 append
- 모든 Slack 대화는 자체적으로 감사 로그 (Slack 히스토리)
- 비용·토큰·도구호출 일일 리포트를 `#agent-ops` 에 자동 post
- 주 1 회 샘플 PR 품질 리뷰 (사람이 직접)

### 6. 무한 루프는 반드시 일어난다 · 미리 막는다

에이전트 간 대화가 가능해지면 A→B→A 루프가 주말 아침에 월 예산을 태운다. 5 중 방어:

1. 봇은 자기가 먼저 스레드를 시작하지 못한다 (cron 제외)
2. 스레드당 봇 발화 최대 N 턴 (기본 10)
3. 체인 깊이 카운터 (3 초과 시 응답 거부)
4. 다른 봇 메시지 기본 무시 (명시적 `@mention` 만 예외)
5. 분당 rate limit 각 봇 자체 throttle

### 7. 예산이 가장 강력한 안전장치

인프라 비용은 거의 0 이지만 Claude API 토큰은 실제 지출이다. 봇별 · 스레드별 · 일별 상한을 AGENT.md 에 명시하고 초과 시 자동 정지 + 사람 알림.

## 무엇이 달라지는가

### 지금

CEO 혼자 Claude Code 를 켜고 작업한다. 슬래시 커맨드로 스킬 호출. Task 툴로 서브에이전트 위임. 세션이 끝나면 컨텍스트 소실.

### 목표 상태

CEO 는 Slack 을 연다. 6 명의 리더가 이미 온라인이다. `@CTO /review PR #234` 한 줄이면 리뷰가 진행되고, "수정해" 한 단어면 실제 커밋이 올라간다. CFO 는 월말이면 자동으로 결산 초안을 DM 으로 보낸다. CMO 는 경쟁사 블로그 변동을 주간 브리핑한다. 리더들끼리는 `#leaders-lounge` 에서 스레드로 협업한다. CEO 는 승인 · 방향 · 전략만 한다.

### 점진적 전환

이 모든 걸 하루에 만들 수 없다. [roadmap.md](./roadmap.md) 에 Sprint 0~4 로 쪼개져 있고, Sprint 0 은 "봇 1 개가 안전하게 도는 것" 에만 집중한다. 11 명 전체 가동은 Sprint 3 이후.

## 반드시 피해야 할 실패 모드

1. **한 번에 다 만들기** — 6 리더 + 5 서브워커를 동시 출시하면 어느 봇이 무슨 문제를 일으키는지 모른다. 1 개씩 shadow → public
2. **자율성 과신** — "알아서 잘 할 것" 기대는 반드시 배신당한다. 승인 게이트 없이는 어떤 파괴적 동작도 허용하지 않는다
3. **감사 생략** — 사람이 안 보는 에이전트는 조용히 망가진다. 로그는 옵션이 아니라 기본값
4. **예산 없음** — API 비용은 주말에 터진다. 캡 없이 런칭 금지
5. **프롬프트 인젝션 무시** — 사용자 메시지와 시스템 지시의 경계가 무너지면 봇이 공격자의 지시를 따른다. guard 훅 필수

## 성공 지표 (Phase 3 완료 기준)

- CEO 가 하루 중 **Slack 에서 90% 이상의 업무 지시** 를 한다 (터미널·웹콘솔 대신)
- 리더 6 명이 **주 1 회 이상 활성** 이다 (상시는 아니더라도)
- CTO 가 제품 레포의 PR 중 **50% 이상을 자동 리뷰** 한다
- **감사 로그로부터** 지난 주 에이전트 활동을 5 분 안에 재구성할 수 있다
- 에이전트 플랫폼 자체 운영비가 **월 $20 미만** 이다 (LLM 토큰 제외)
- 새 리더 1 명 추가에 **30 분 미만** 소요된다 (스캐폴드 + persona 작성 + 배포)
