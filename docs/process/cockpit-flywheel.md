# cockpit 플라이휠 — 측정·검증·진화

> cockpit 이 시간이 갈수록 **더 똑똑해지는 루프**를 명시한다. 아티팩트는 포크 가능하지만
> **이 루프의 속도와 축적된 컨텍스트는 못 베낀다** — 그게 해자다.

```
세션 → 발견(finding) → 원장(ledger) → [반복/실사고] → 승격 → 표준·골든셋·[[hard-won-conventions]]
                                                              ↓
                                          강제(hooks·frontmatter) → 다음 세션이 더 똑똑 → 측정 → 가지치기
```

## 이미 강한 것 (건드리지 않는다)

`humans/skills/review/` 에 **리뷰어 레벨 측정·검증**이 이미 구현돼 있다. 아래는 **재확인용**이며, 새로 만들지 말 것:

- **원장** `docs/review/ledger.jsonl` — 발견을 안정 키로 정규화, 실행 간 `fixed/new/open` diff. 스칼라 점수보다 1급.
- **결정론 점수** — 발견에서 **스크립트가** 계산(LLM 산술 금지). 게이트(불리언)가 스칼라보다 우선.
- **objective 측정** — LOC·CC·lint·CVE·secret 은 **도구 측정값으로만** 판정(눈대중 금지).
- **골든셋** `fixtures/` — 라벨된 결함 → `eval.py` precision/recall, `clean_good.py` 거짓양성 감시, PASS 임계 0.8, `RULESET_VERSION`.
- **적대적 검증** — High/Critical 강제, confidence 부여.

## 갭을 채우는 3개 기어 (여기가 신규)

### 기어 1 — 발견 → 표준 승격 (루프 닫기)

원장의 발견은 대부분 일회성이다. 그러나 **반복되면 규칙이 될 자격**이 있다.

**승격 트리거** (하나라도 충족):
- 같은 안정 키가 **3회 이상 실행에서 `open`** 으로 잔존, 또는 **2개 이상 프로젝트**에서 등장.
- **실제 사고/High+ 버그**를 유발(1회로도 즉시).

**승격 대상** (셋 다 하는 게 이상적):
1. `core/standards/` 해당 규칙 추가/강화 (재발 방지의 근원).
2. `fixtures/cases/` 골든셋 케이스 + `expected.jsonl` 한 줄 (리뷰어가 앞으로 반드시 잡도록).
3. edge(비자명·실사고)면 [[hard-won-conventions]] 에 provenance 와 함께 등재.

> 승격 없이 원장만 쌓이면 **같은 부채를 영원히 재발견**한다. 이 기어가 플라이휠의 회전축이다.

### 기어 2 — cockpit 시스템 계측 (프로젝트를 넘어선 롤업)

프로젝트별 원장은 있으나, **cockpit 자체가 효과 있는가**는 별도 지표가 필요하다. 분기마다 집계:

| 메타 지표 | 정의 | 소스 |
|-----------|------|------|
| **골든셋 P/R 추세** | RULESET 버전별 precision/recall | `eval.py` 출력 이력 |
| **재발률(recurrence)** | `fixed` 된 발견이 이후 다시 `new` 로 등장한 비율 | 프로젝트 원장들 |
| **규칙 fire-rate** | 각 표준 규칙이 실제 발견을 잡은 횟수 (0 = 죽은 규칙 후보) | 발견 category ↔ 규칙 매핑 |
| **open-debt 추세** | `open` 발견 수의 시계열 (부채 증가/감소) | 프로젝트 원장들 |

> 기록: `docs/process/cockpit-metrics.jsonl` (분기 1줄). 안 재면 개선도 자랑도 근거 없음.
>
> **구현**: `scripts/cockpit-metrics.py` 가 원장에서 open-debt·추세·재발률·fire-rate 를
> 계산해 이 파일에 append 하고, **승격 후보**(안정 키 ≥3회 open 또는 2+프로젝트)를
> 자동 출력한다 — 기어1 승격의 넛지. `--ledger <프로젝트 원장>` 로 cross-project 집계.
> `--check` 는 기록 없이 출력만. (적용은 사람 — `/review:promote`)

### 기어 3 — 유지보수 사이클 (드리프트·낡음 방지)

**분기 1회 체크리스트**:
- [ ] `scripts/cockpit-metrics.py` 실행 → open-debt 추세·재발률·승격 후보 확인, 계측 파일에 기록.
- [ ] 골든셋 실행(`eval.py`) → P/R 회귀 없으면 통과, 있으면 원인 규명.
- [ ] **fire-rate 0 규칙 가지치기** — `cockpit-metrics.py` 의 `fire_rate_top` 에 없는(한 번도 발견을 못 잡은) 규칙은 삭제 후보(과잉 규칙은 준수율을 떨어뜨린다).
- [ ] **모델 버전 태깅** — 위임 에이전트/메인 모델이 바뀌면, 골든셋 재통과 **전엔** 점수를 신뢰하지 않는다.
- [ ] 표준 변경 시 `RULESET_VERSION` bump + 골든셋 회귀 확인.

## 모델 버전 태깅 규칙

표준·룰셋은 **"어떤 모델에서 검증됐는지"** 를 안다. 모델 업그레이드는 조용한 회귀의 최대 원인이므로:
- 위임 에이전트 모델 변경 → **골든셋 먼저**(기어 3) → 통과 후에만 새 모델로 리뷰 신뢰.
- 회귀 시 규칙이 아니라 **프롬프트/앵커**를 먼저 의심(모델이 기준을 다르게 해석).
