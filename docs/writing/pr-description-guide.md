# PR 설명 가이드

> 기준: 리뷰어가 **5분 안에** 변경 의도와 영향 범위를 파악할 수 있는 PR.

## 제목

- **70자 이하**, 본문으로 상세 설명을 미루세요
- `<type>: <요약>` 형식 권장 (Conventional Commits 규약과 동일)
- 브랜치 접두사와 일치: `feature/`, `fix/`, `chore/`

예:
- ✅ `feat(mcp): Keychain 기반 비밀값 저장소 도입`
- ❌ `feat: 다양한 변경 (리팩토링 포함)`

## 본문 구조

```markdown
## Summary
<1-3줄. "왜" + "무엇을" 바꿨는지>

## Why
<배경·문제점·관련 티켓. 리뷰어가 코드만 봐서는 알 수 없는 맥락>

## What Changed
- <카테고리1> — <한 줄>
- <카테고리2> — <한 줄>

## Test Plan
- [ ] 단위 테스트 X개 추가/통과
- [ ] 통합 테스트: <시나리오>
- [ ] 수동 검증: <스텝>

## Screenshots / Recordings (UI 변경 시)

## Risks / Rollback
<장애 가능성, 롤백 방법, 마이그레이션 필요 여부>

## Checklist
- [ ] 셀프 리뷰 완료
- [ ] 테스트 추가/수정
- [ ] 문서 업데이트 (해당 시)
- [ ] 하위 호환성 확인 (API/DB)
- [ ] 비밀값·시크릿 노출 없음
```

## 크기 가이드

| 변경 규모 | 파일 수 | 라인 수 | 리뷰어 대응 |
|----------|--------|--------|------------|
| S | <5    | <100   | 당일 리뷰 기대 |
| M | 5-15  | 100-500 | 1영업일 |
| L | 15-30 | 500-1000 | 사전 설계 공유 필요 |
| XL | >30  | >1000  | **분할 권장** |

`/ci:pr-enhance` 는 L 이상에서 자동으로 분할 제안을 시도합니다.

## Why 섹션 작성 팁

코드만 봐서는 **알 수 없는 정보**만 적습니다:
- 사용자가 겪은 증상 / 장애 로그
- 관련 인시던트, ADR, 설계 문서 링크
- 대안을 고려했다면 왜 기각했는지
- 성능 수치 (before/after)

## 리뷰 요청

- **Draft** 상태로 먼저 올려 CI 통과 확인
- 리뷰어 1명 최소, 보안·인프라 변경은 2명
- 질문 스레드가 해결되면 resolve 를 요청자가 직접 클릭하지 않고 리뷰어가 확정

## 머지 정책

- **Squash merge 기본** (기능 단위 커밋 1개)
- 커밋 이력이 의미 있는 리팩토링 시리즈는 **Rebase merge**
- Merge commit은 지양
