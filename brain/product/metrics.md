# 프로덕트 지표 기준

> 기능을 만들기 전에 **"성공을 어떻게 측정할 것인가"** 를 먼저 정의합니다. 지표 없이 런치하지 않습니다.

## 지표의 3계층

```
[North Star] — 제품 전체의 건강도 (분기 단위로 봄)
     ↓
[Goal Metric] — 이번 기능/캠페인의 성공 지표 (기능 단위)
     ↓
[Guardrail Metric] — 해치면 안 되는 지표 (같이 봄)
```

### North Star Metric

- **제품 가치 = 단 하나의 숫자**. 모호하면 North Star 가 아닙니다.
- 예시:
  - SaaS: 주간 활성 워크스페이스 수
  - 학습 앱: 주간 완료된 학습 세션 수
  - 커머스: 주간 재구매 유저 수
- **에이션 지표 금지**: "방문자 수", "가입 수" 는 활동이지 가치가 아님.

### Goal Metric (기능별)

새 기능은 **1개의 Goal Metric** 을 가져야 합니다. 없으면 기능을 만들지 않습니다.

- 선행 지표 선호 (후행보다): "알림 수신율" > "다음 달 리텐션"
- 타겟 값 명시: "클릭률 +2pp" 식으로 숫자.
- 측정 기간 명시: "런치 후 2주".

### Guardrail Metric

Goal 을 달성하려다 해치면 안 되는 것:

- 성능 (p95 응답시간)
- 에러율
- 상위 퍼널 (가입 전환율)
- 사용자 만족 (CSAT, NPS)

**원칙**: Goal 이 +10% 됐는데 Guardrail 이 -5% 면 **롤백 또는 재설계**.

## 활성화·리텐션 기본 정의

용어는 프로젝트마다 달라지지 않도록 여기서 못 박습니다.

| 지표 | 정의 |
|------|------|
| **D1 리텐션** | 가입일(D0) 다음날(D1) 에 1회 이상 핵심 액션 수행한 유저 비율 |
| **D7 리텐션** | 가입 후 7일차에 1회 이상 핵심 액션 수행한 유저 비율 |
| **D30 리텐션** | 가입 후 30일차에 1회 이상 핵심 액션 수행한 유저 비율 |
| **활성화 (Activation)** | 가입 후 **X일 이내** 에 **Y번** 핵심 액션 수행 — X, Y 는 제품별로 한 번 정의하고 바꾸지 않음 |
| **WAU** | 최근 7일 중 1회 이상 핵심 액션 수행한 고유 유저 |
| **MAU** | 최근 30일 중 1회 이상 핵심 액션 수행한 고유 유저 |

> **핵심 액션 (Core Action)** 은 제품별로 1개 정의. 예: 학습 앱 → "세션 1개 완료", SaaS → "프로젝트 1개 생성".
> 정의를 바꾸면 이전 지표는 비교 불가 — 변경 시 ADR 필수.

## 측정 인프라 최소 요건

- **이벤트 수집**: `user_id`, `event_name`, `timestamp`, `properties` 4개 필드는 필수.
- **서버 사이드 이벤트 우선**: 클라이언트 이벤트는 손실됨 (애드블록, 앱 크래시).
- **PII 분리**: 이벤트 페이로드에 이메일·이름 포함 금지 (`@brain/ai/ai-usage.md` 와 동일 원칙).
- **대시보드 한 곳**: 매일 보는 지표는 한 URL 에 모음. 여러 툴 돌아다니지 말 것.

## 지표 없이 금지되는 것

- 런치: Goal Metric 정의 없이 프로덕션에 기능 배포 금지.
- A/B 테스트: 사전 정의된 성공 기준 없이 실험 시작 금지 (p-hacking 방지).
- 리팩터링 주장: "성능 개선" 을 이유로 드는 리팩터링은 before/after 숫자 없으면 기각.

## 체크리스트 (기능 런치 전)

- [ ] Goal Metric 1개가 정의돼 있는가? (타겟 값 + 측정 기간 포함)
- [ ] Guardrail Metric 최소 1개 (대개 성능 또는 에러율)
- [ ] 이벤트가 프로덕션에서 실제로 수집되는 것을 런치 전 확인했는가?
- [ ] 대시보드에 패널이 추가됐는가?
- [ ] 롤백 기준이 숫자로 정의돼 있는가? (예: "에러율 >1% 면 5분 내 롤백")
