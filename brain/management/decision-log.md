# 의사결정 로그 (ADR) 프로세스

> 1인 창업이라도 **6개월 뒤 자기 자신을 설득**하기 위해 의사결정을 기록합니다. 팀이 생겼을 때 가장 값진 자산이 됩니다.

## 언제 ADR 을 쓰는가

다음 중 하나라도 해당하면 ADR 을 씁니다:

- **되돌리기 어려운 선택** — 프레임워크, 데이터베이스, 인증 방식, 결제 프로바이더
- **비자명한 트레이드오프** — "왜 단순한 방법 대신 이걸 골랐지?" 질문이 나올 만한 경우
- **외부 제약에 기반한 결정** — 법적, 비용, 계약상 제약
- **여러 대안을 진지하게 비교한 경우** — 비교 과정 자체가 미래의 자산

## 쓰지 않아도 되는 경우

- 라이브러리 버전 업그레이드 (CHANGELOG 로 충분)
- 네이밍·코드 스타일 (coding-guidelines 에 이미 있음)
- 1회성 스크립트·임시 해결책

## 형식

- **템플릿**: `@brain/templates/adr-template.md`
- **위치**: 프로젝트별 `docs/adr/NNNN-title-in-kebab.md` (NNNN 은 4자리 연번)
- **길이**: 1-2페이지. 길면 결정이 아닌 설계 문서일 가능성.
- **작성 가이드**: cockpit 레포 `docs/writing/adr-writing-guide.md` (standards submodule 밖 — 소비 프로젝트엔 없을 수 있음)

## 상태 라이프사이클

```
Proposed → Accepted → (Deprecated | Superseded by ADR-XXXX)
```

- **Proposed** 상태로 시작, 결정 확정되면 **Accepted**.
- 나중에 뒤집히면 삭제하지 말고 **Superseded** 로 표시 + 새 ADR 생성.
- 과거 결정의 맥락을 지우지 않는 것이 핵심입니다.

## 1인 운영 팁

- **"나중에 쓰지" 가 제일 위험** — 결정한 그 주에 작성. 기억은 48시간 뒤 왜곡됩니다.
- **완벽하지 않아도 됨** — 3줄짜리 ADR 도 없는 것보단 낫습니다.
- **분기별 리뷰**: 3개월마다 `docs/adr/` 읽어보기. 여전히 유효한지, 뒤집어야 할 것 없는지.

## 체크리스트

새 ADR 작성 시:

- [ ] 결정 제목이 "왜" 가 아닌 "무엇" 에 답하는가? (예: "PostgreSQL 을 쓴다" O, "성능을 고려한다" X)
- [ ] Context 에 제약 조건이 명시돼 있는가?
- [ ] Alternatives 에 최소 1개 이상의 다른 선택지가 있는가?
- [ ] Consequences 에 Negative 도 적혀 있는가? (Positive 만 있으면 의심)
- [ ] 6개월 뒤의 자신이 읽고 이해할 수 있는가?
